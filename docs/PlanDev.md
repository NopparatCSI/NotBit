# แผนแบ่งงาน Game Item Marketplace — Developer 3 คน ภายใน 5 วัน

## 1. เป้าหมายและขอบเขตส่งมอบ

ส่งระบบสาธิตบน **Sepolia ที่ซื้อขายได้จริงครบเส้นทาง** โดย Developer คนที่ 1 วางโครงสร้างและข้อตกลงการเชื่อมต่อภายในวันแรก จากนั้นทั้งสามคนพัฒนาพร้อมกัน รวมกำลังทำงาน **15 คน-วัน**

**งานที่ต้องเสร็จในสัปดาห์นี้**

- เข้าใช้งานด้วย MetaMask และแยก Wallet ผู้ซื้อ ผู้ขาย Admin และ Super Admin
- ตลาดสินค้า รายละเอียดสินค้า และเพิ่ม/แก้ไข/พักประกาศ
- แชทข้อความ ผู้ขายสร้างข้อเสนอ และผู้ซื้อฝากเงิน
- แนบหลักฐาน ยืนยันส่ง ยืนยันรับ และแบ่งเงินผู้ขาย 95% / แพลตฟอร์ม 5%
- เปิดข้อพิพาท และให้ Admin ตัดสินคืนเต็มจำนวนหรือจ่ายตามดีล
- ออเดอร์เกินกำหนดเข้าสู่คิวตรวจ โดยไม่มีการจ่ายหรือคืนอัตโนมัติ
- Super Admin หยุดและเปิดรับเงินฝากใหม่
- หน้าเว็บภาษาไทย ธีมเข้ม รองรับมือถือ และแสดงข้อความว่าเป็นระบบทดสอบ

**งานเลื่อนไปรอบถัดไป**

ระบบแต่งตั้ง/เปลี่ยน/ถอนผู้ดูแล รีวิว การแจ้งเตือนแยกหน้า รายงานยอดขาย การจัดการผู้ใช้และระงับบัญชี ระบบรายงานประกาศ และตัวกรองขั้นสูง

รอบนี้กำหนด Admin และ Super Admin ตอนติดตั้ง และ **ไม่มีช่องทางเปลี่ยนบทบาทภายหลัง** ทั้งบนเว็บและ Contract การเพิ่มระบบจัดการบทบาทจึงเป็นงานรอบใหม่ที่ต้องออกแบบและทดสอบแยก เพราะ Contract รุ่นแรกไม่รองรับการอัปเกรด

## 2. แบ่งเจ้าของงานและสิ่งที่ต้องส่งต่อ

| ผู้รับผิดชอบ | งานหลัก | ผลงานที่ต้องส่ง |
|---|---|---|
| **Developer 1 — หัวหน้าทีม / โครงสร้าง / Contract** | ตั้งโปรเจกต์ เครื่องมือทดสอบ โครงฐานข้อมูล ระบบเข้าสู่ระบบ ตัวตรวจสิทธิ์ส่วนกลาง Contract และการติดตั้ง | โปรเจกต์ที่ทุกคนรันได้ ข้อตกลง API/ข้อมูล ABI ชุดทดสอบ Contract และระบบออนไลน์ |
| **Developer 2 — ตลาด / ผู้ซื้อ / ผู้ขาย** | ทำหน้าจอและ API ของประกาศ แชท ข้อเสนอ และออเดอร์ เชื่อม Wallet กับการซื้อขาย | เส้นทางเลือกสินค้า → แชท → ฝาก → ส่ง → รับ พร้อมหน้าผู้ซื้อและผู้ขาย |
| **Developer 3 — หลักฐาน / Admin / งานเบื้องหลัง** | จัดเก็บและลงนามใบรับหลักฐาน หน้าข้อพิพาท คำตัดสิน ประวัติผู้ดูแล และระบบอ่านสถานะจากบล็อกเชน | ระบบหลักฐานส่วนตัว หน้า Admin/Super Admin และฐานข้อมูลที่ตรงกับ Contract |

**ขอบเขตความรับผิดชอบร่วม**

- แต่ละคนรับผิดชอบทั้งหน้าจอ API และการทดสอบของส่วนตนเอง
- คนที่ 1 เป็นเจ้าของรูปแบบข้อมูลร่วมและตรวจการแก้ไขที่กระทบหลายส่วน
- คนที่ 2 เขียนกฎเข้าถึงข้อมูลตลาดและแชท คนที่ 3 เขียนกฎหลักฐานและผู้ดูแล โดยคนที่ 1 ตรวจทาน
- คนที่ 3 ตรวจ Contract ร่วมกับคนที่ 1 โดยเน้นเงิน หลักฐาน และสิทธิ์
- รวมงานทุกวันผ่าน Pull Request ที่มีผู้ตรวจอย่างน้อยหนึ่งคน ไม่รอรวมครั้งเดียววันสุดท้าย

**สิ่งที่คนที่ 1 ต้องเตรียมก่อนกระจายงานเต็มรูปแบบ**

1. Repository เดียว แยกเว็บ Contract และชุดข้อมูล/อินเทอร์เฟซที่ใช้ร่วมกัน
2. คำสั่งติดตั้ง รัน ทดสอบ และไฟล์ตัวอย่างการตั้งค่า โดยไม่มีค่าลับ
3. โครงหน้าเว็บ การเชื่อม Wallet การเข้าสู่ระบบ และตัวตรวจผู้ใช้/ผู้ดูแล
4. โครงฐานข้อมูลเริ่มต้น กฎการตั้งชื่อ และข้อมูลสาธิตสามเกม
5. รายการสถานะออเดอร์ รูปแบบ API ลายเซ็น และ ABI ฉบับเริ่มต้น
6. ข้อมูลจำลองและตัวเชื่อมต่อจำลอง เพื่อให้คนที่ 2–3 ทำงานได้ก่อน Contract เสร็จ

ให้ส่งข้อ 1–3 **ภายในเที่ยงวันแรก** และล็อกข้อ 4–6 **ก่อนจบวันแรก** ระหว่างนั้นคนที่ 2 เริ่มโครงหน้าตลาด ส่วนคนที่ 3 เริ่มโครงหน้า Admin และรายการทดสอบสิทธิ์ได้

## 3. โครงสร้างระบบและข้อตกลงที่ทุกคนใช้ร่วมกัน

ใช้เทคโนโลยีตามเอกสารเดิม: Next.js + TypeScript, Tailwind + shadcn/ui, Supabase, wagmi + viem, Solidity + OpenZeppelin, Hardhat 3, Vitest และ Playwright

ใช้ Supabase Web3 Auth สำหรับยืนยัน Wallet ซึ่งรองรับ Ethereum อยู่แล้ว และใช้ Supabase Cron เรียก Edge Function สำหรับงานตรวจสถานะตามเวลา ตาม [เอกสาร Web3 Auth](https://supabase.com/docs/guides/auth/auth-web3) และ [เอกสาร Scheduled Functions](https://supabase.com/docs/guides/functions/schedule-functions) คนที่ 1 ต้องตรวจความเข้ากันได้และล็อกเวอร์ชันเครื่องมือทั้งหมดในวันแรก โดยอิงข้อกำหนดจาก [Hardhat 3](https://hardhat.org/docs/getting-started)

**การแบ่งข้อมูล**

- Contract เป็นแหล่งข้อมูลหลักเรื่องเงิน สถานะออเดอร์ และสิทธิ์ผู้ดูแลบนเชน
- ฐานข้อมูลเก็บโปรไฟล์ ประกาศ แชท ข้อเสนอ ข้อตกลง หลักฐาน ข้อพิพาท และประวัติการทำงาน
- เพิ่มตารางบันทึกเหตุการณ์บล็อกเชนและจุดที่อ่านถึง เพื่อกู้การทำงานหลังหยุดหรือประมวลผลซ้ำ
- รูปประกาศเป็นสาธารณะ หลักฐานเป็นส่วนตัว และตรวจสิทธิ์ก่อนออกลิงก์ดูไฟล์
- ค่าลับของบริการและกุญแจลงนามใบรับหลักฐานอยู่ฝั่งเซิร์ฟเวอร์เท่านั้น

**จุดเชื่อมต่อที่ต้องตกลงก่อนแยกทำงาน**

| จุดเชื่อมต่อ | ผู้รับผิดชอบ | ข้อตกลง |
|---|---|---|
| บัญชีและสิทธิ์ | คนที่ 1 | คืนรหัสผู้ใช้ Wallet และบทบาทจากข้อมูลที่ตรวจสอบแล้ว ไม่รับบทบาทที่ผู้ใช้ส่งมาเอง |
| ประกาศ แชท ข้อเสนอ | คนที่ 2 | API สำหรับดู/แก้ประกาศ เปิดห้อง ส่งข้อความ และสร้างข้อเสนอที่ผู้ขายลงนาม |
| หลักฐาน | คนที่ 3 | รับไฟล์ ตรวจชนิด/ขนาด/สิทธิ์ เก็บ Hash แล้วคืนใบรับที่ระบบลงนามให้คนที่ 2 ใช้เรียก Contract |
| ข้อพิพาทและคำตัดสิน | คนที่ 3 | เก็บเหตุผลและหลักฐานก่อนส่งธุรกรรม ผูก Hash คำตัดสินกับออเดอร์และผลตัดสิน |
| ธุรกรรม Contract | คนที่ 1 | ส่ง ABI รูปแบบลายเซ็น เหตุการณ์ และรหัสข้อผิดพลาดให้คนที่ 2–3 ใช้ร่วมกัน |
| สถานะจากเชน | คนที่ 3 | อ่านเหตุการณ์และอัปเดตฐานข้อมูล คนที่ 2 ใช้ข้อมูลนี้แสดงผลและติดตามธุรกรรมทันที |

จำนวนเงินใช้ **wei แบบจำนวนเต็ม** และส่งผ่าน JSON เป็นข้อความ ห้ามใช้เลขทศนิยมสำหรับคำนวณเงิน รหัสออเดอร์และวิธีสร้าง Hash ต้องใช้ชุดฟังก์ชันร่วมเดียวกัน

**สถานะและกติกาที่ห้ามแต่ละคนตีความต่างกัน**

- ข้อเสนอ: `OPEN → FUNDED` หรือ `EXPIRED` มีอายุ 30 นาที
- ออเดอร์บน Contract: `FUNDED → DELIVERED → RELEASED`
- เมื่อเปิดข้อพิพาทหรือยกระดับออเดอร์หมดเวลา: `FUNDED/DELIVERED → IN_REVIEW`
- Admin ตัดสินจาก `IN_REVIEW` ไป `REFUNDED` หรือ `RELEASED` ได้ครั้งเดียว
- เกิน 24 ชั่วโมงหลังฝาก หรือ 48 ชั่วโมงหลังยืนยันส่ง ให้ Contract ปฏิเสธเส้นทางปกติ แม้งานเบื้องหลังยังไม่ทำงาน
- คำนวณค่าบริการ `floor(amount × 500 / 10000)` และให้ผู้ขายรับส่วนที่เหลือ
- เมื่อโอนเงินล้มเหลว ให้บันทึกยอดค้างรับ และผู้รับถอนยอดของตนได้ โดยไม่กระทบออเดอร์อื่น
- สถานะธุรกรรมแยกจากสถานะออเดอร์ และรออย่างน้อย 3 confirmations ก่อนแสดงเงินฝากว่าสำเร็จ

**ข้อกำหนด Contract ที่คนที่ 1 ต้องส่ง**

`fundOrder`, `confirmDelivery`, `confirmReceipt`, `openDispute`, `escalateExpiredOrder`, `resolveDispute`, `withdrawPendingPayout` และคำสั่งหยุด/เปิดรับเงินฝาก

ข้อเสนอใช้ EIP-712 ผูกคู่ค้า ราคา ประกาศ ออเดอร์ วันหมดอายุ Hash ข้อตกลง เครือข่าย และ Contract ส่วนใบรับหลักฐานต้องผูกออเดอร์ ผู้ส่ง ประเภทการยืนยัน และ Hash เพื่อใช้ข้ามออเดอร์หรือข้ามขั้นตอนไม่ได้

หนึ่งประกาศรับเงินสำเร็จได้เพียงหนึ่งออเดอร์ โดย Contract เป็นผู้บังคับกติกา การแก้ประกาศไม่เปลี่ยนข้อเสนอที่ลงนามแล้วหรือข้อตกลงของออเดอร์

**ข้อกำหนดงานเบื้องหลังของคนที่ 3**

อ่านเหตุการณ์ทุกหนึ่งนาที บันทึกเลขบล็อกและ Hash ป้องกันเหตุการณ์ซ้ำด้วยรหัสธุรกรรมและลำดับ log หากพบการเปลี่ยนบล็อกให้ย้อนถึงจุดร่วมและสร้างสถานะที่เกี่ยวข้องใหม่ เมื่อ RPC ขัดข้องให้คงสถานะรอตรวจสอบและลองใหม่ ห้ามแสดงสำเร็จจาก Transaction Hash เพียงอย่างเดียว

## 4. ตารางทำงาน 5 วันและจุดตรวจรับ

| วัน | Developer 1 | Developer 2 | Developer 3 | จุดตรวจรับ |
|---|---|---|---|---|
| **วัน 1 — ตั้งฐาน** | ตั้งโปรเจกต์/บริการ ระบบ login โครงข้อมูล อินเทอร์เฟซ และชุดทดสอบ | โครงตลาด รายละเอียดสินค้า หน้าผู้ซื้อ/ผู้ขาย ด้วยข้อมูลจำลอง | โครง Admin แบบข้อมูลหลักฐาน กฎสิทธิ์และชุดกรณีทดสอบ | ทุกคนรันโปรเจกต์ได้ Login ได้ และใช้ข้อตกลงข้อมูลเดียวกัน |
| **วัน 2 — สร้างเส้นทางหลัก** | Contract ฝาก–ส่ง–รับ ค่าบริการ ลายเซ็น และป้องกันฝากซ้ำ | ประกาศ แชท ข้อเสนอ และหน้ารอฝากเงินจริงบนเครือข่ายทดสอบในเครื่อง | อัปโหลดหลักฐาน ใบรับลงนาม การอ่านเหตุการณ์ และบันทึกจุดอ่าน | ฝากเงินจากหน้าเว็บได้ และเชื่อมหลักฐานกับออเดอร์ได้ |
| **วัน 3 — เชื่อมครบวงจร** | ข้อพิพาท หมดเวลา ยอดค้างรับ หยุดฝาก และติดตั้ง Sepolia หลังทดสอบผ่าน | ยืนยันส่ง/รับ เปิดข้อพิพาท สถานะธุรกรรม และข้อผิดพลาด Wallet | คิวตรวจ คำตัดสินผ่าน Wallet ประวัติ Admin และ Cron | ซื้อขายสำเร็จและคืนเงินได้ครบเส้นทางบน Sepolia |
| **วัน 4 — ทดสอบรวม** | ตรวจเงิน ลายเซ็น การเรียกซ้ำ และการตั้งค่าระบบ | ทดสอบผู้ซื้อ/ผู้ขาย มือถือ รีเฟรชหน้า และการทำงานพร้อมกัน | ทดสอบสิทธิ์ไฟล์ คำตัดสินซ้ำ หมดเวลา และกู้การอ่านเหตุการณ์ | ผ่านกรณีหลัก ไม่มีข้อผิดพลาดเรื่องเงินหรือสิทธิ์ |
| **วัน 5 — ส่งมอบ** | ตรวจรุ่นส่งมอบ ยืนยัน Contract บน explorer และคู่มือติดตั้ง | เก็บรายละเอียดหน้าจอ คู่มือผู้ใช้ และซ้อมสาธิต | คู่มือ Admin รายงานทดสอบ และข้อมูลสาธิต | ส่งลิงก์ โค้ด ผลทดสอบ และสาธิตตามรายการตรวจรับ |

**วิธีควบคุมงาน**

- ประชุมเช้า 15 นาที ระบุงานวันนี้ สิ่งที่ต้องรับจากเพื่อน และอุปสรรค
- ช่วงบ่ายตรวจการเชื่อมต่อ ส่วนท้ายวันรวมงานและสาธิตผลจริง
- หลังจบวัน 3 หยุดเพิ่มฟีเจอร์ ให้วัน 4–5 สำหรับแก้ปัญหาและส่งมอบ
- หากจุดตรวจรับไม่ผ่าน ให้แจ้งผลกระทบในวันนั้น ลดงานตกแต่งก่อน และไม่ตัดการตรวจเงิน ลายเซ็น หรือสิทธิ์เพื่อให้ทันกำหนด

| หมดเวลา | ปฏิเสธการยืนยันปกติหลังเส้นตาย เงินยังพักและ Admin ตรวจต่อได้ |
| เงินและลายเซ็น | ปฏิเสธยอดผิด ผู้เรียกผิด ลายเซ็นหมดอายุ หลักฐานผิดออเดอร์ ซื้อของตัวเอง และฝากประกาศเดียวกันซ้ำ |
| การทำงานพร้อมกัน | ฝากพร้อมกันสำเร็จได้หนึ่งรายการ ยืนยันรับชนกับเปิดข้อพิพาทไม่ทำให้จ่ายซ้ำ |
| หลักฐานและสิทธิ์ | ข้ามใบรับไม่ได้ บุคคลภายนอกเปิดไฟล์ไม่ได้ แชทและหลักฐานเดิมแก้ทับไม่ได้ |
| ยอดค้างรับ | ผู้รับถอนยอดตนเองได้ และยอดพักรวมกับยอดค้างรับมีเงินรองรับครบ |
| ระบบขัดข้อง | Wallet ปฏิเสธ เครือข่ายผิด RPC ล่ม รีเฟรชหน้า หรือเหตุการณ์ซ้ำ ไม่ทำให้แสดงสำเร็จเท็จ |
| ผู้ดูแล | ผู้ใช้ทั่วไปตัดสินไม่ได้ Admin หยุดฝากไม่ได้ และการหยุดฝากยังเปิดให้จัดการออเดอร์เดิม |

ทดสอบเวลา 24/48 ชั่วโมงด้วยการเลื่อนเวลาในเครือข่ายทดสอบในเครื่อง ส่วน Sepolia ใช้ค่าจริงและเตรียมออเดอร์ค้างล่วงหน้าสำหรับสาธิต ห้ามลดเวลาของ Contract ส่งมอบเพียงเพื่อให้สาธิตเร็วขึ้น

**ชุดส่งมอบ**

- ลิงก์เว็บสาธิต และที่อยู่ Contract บน Sepolia ที่ตรวจสอบซอร์สได้
- โค้ดเว็บ Contract โครงสร้างฐานข้อมูล กฎสิทธิ์ และข้อมูลสาธิต
- ชุดทดสอบอัตโนมัติ พร้อมรายงานผลการสาธิตด้วย MetaMask จริง
- ตัวอย่างการตั้งค่า คู่มือติดตั้ง คู่มือผู้ใช้และผู้ดูแล
- รายการข้อจำกัดและงานรอบถัดไป โดยระบุชัดว่าระบบจัดการผู้ดูแลเต็มรูปแบบยังไม่อยู่ในรุ่นนี้

**สมมติฐานของแผน**

ทั้งสามคนทำงานเต็มเวลาและทำ Full-stack ได้ คนที่ 1 มีประสบการณ์ Solidity/Contract testing บัญชี Vercel, Supabase, Alchemy และ Wallet พร้อม Sepolia ETH เตรียมได้เช้าวันแรก

ระยะเวลา 5 วันเป็นเป้าหมายสำหรับ **ระบบสาธิตตามขอบเขตที่ลดแล้ว** ไม่ใช่แผนส่งครบเอกสารต้นฉบับ หากบริการภายนอกไม่พร้อม ให้ส่งระบบที่รันในเครื่องได้และระบุรายการติดตั้งที่ค้าง โดยยังไม่ถือว่าผ่านเกณฑ์ออนไลน์บน Sepolia
